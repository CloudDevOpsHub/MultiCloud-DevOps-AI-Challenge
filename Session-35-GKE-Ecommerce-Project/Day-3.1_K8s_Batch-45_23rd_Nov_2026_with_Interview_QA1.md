## Decisions Made

- **Deployment over ReplicaSet:** ReplicaSet is considered outdated; all production and interview discussions should reference **Deployment** as the standard approach for managing pods. 
- **NGINX should be described as a "web server" or "frontend"** in interviews — never just "NGINX" — to signal microservices awareness and command higher perceived value. 
- **IP-to-IP communication is discouraged** in Kubernetes; all pod-to-pod communication should use **service names** to avoid broken connections when pod IPs change. 
- **Production (prod) must always be a separate cluster** — never merged with dev/QA — both for interview framing and real-world practice. 
- **Kubernetes-native Secrets** are base64-encoded (easily decoded), so Vault is preferred for sensitive information in production environments; these are treated as separate, non-overlapping concepts. 
- **Cloud Shell is the default connection method** for GKE; running the `gcloud` connect command from a local machine requires installing and configuring the **Gcloud SDK**.

## Architecture Components Reviewed

A quick interactive revision covered all major Kubernetes components before moving to hands-on work:

- **kubectl:** Command-line utility to interact with the control plane; key command families include `get`, `describe`, `delete`, `exec`, and `edit`. 
- **API Server:** Middleware/brain of the cluster; handles all API requests between master node, worker nodes, and kubectl. 
- **Controller Manager:** Responsible for creating and managing cluster resources such as replicas, namespaces, and service accounts. 
- **Scheduler:** Finds the best worker node for a pod based on available resources and rules. 
- **etcd:** Key-value data store that saves the state of all activities happening in the Kubernetes cluster. 
- **Kubelet:** Agent present on every worker node; reports cluster status back to the master node. 
- **Kube Proxy:** Manages network rules and exposes pods externally; supports three service types — **Load Balancer** (internet-facing), **NodePort** (node-level), and **ClusterIP** (cluster-internal). 
- **Container Runtime:** Runs containerized applications inside pods; GKE uses **Docker** as the default container runtime.

## GKE Cluster Creation (3-Click Walkthrough)

- Navigate to **Kubernetes Engine → Clusters → Create**. 
- Add a **node pool** (default config is inherited automatically). 
- Set node count to **3** (one per zone = 9 nodes total if left at default 3-per-zone; keep at 3 for learning). 
- OS: default (Container-Optimized OS); storage: **30 GB per node** = 90 GB total. 
- Cluster creation takes approximately **2–3 minutes**; three corresponding VMs appear in Compute Engine. 
- Connect command generated by GCP: `gcloud container clusters get-credentials <cluster-name> --region <region> --project <project>` — this generates the **kubeconfig file**, a key interview term. 
- To run from a local machine: install **Gcloud SDK**, run `gcloud configure`, then execute the connect command.

## Namespaces

- Logical isolation of environments within a cluster. 
- **Real-world examples shared by students:**
    - Monitoring tools in a dedicated `monitoring` namespace. 
    - Storage components (PVCs) in a `pvc` namespace. 
    - Deployment/CI-CD tools in a `deployment` namespace. 
    - Project-based microservices in project-specific namespaces. 
    - QA and Dev can share a namespace to save costs, but **prod is always a separate cluster**. 
- Can be created via `kubectl create namespace` command or via YAML.

## Pods and Deployments

### Pods

- Smallest running unit in Kubernetes; contains one container and one volume in standard practice. 
- Multiple containers per pod are possible but increase management complexity — not recommended. 
- Pod design decisions are made by the **architect or dev team**, not unilaterally by the DevOps engineer. 

### ReplicaSet vs. Deployment

- **ReplicaSet (outdated):** `kubectl run nginx --image=nginx --replicas=3` creates 3 pods, but if one dies, there is no automatic recovery — no manager monitors desired state. 
- **Deployment (current standard):** `kubectl create deployment nginx-deploy --image=nginx` creates a deployment that continuously maintains the desired pod count. 
    - If a pod is deleted, the deployment automatically recreates it within ~45 seconds. 
    - Desired state is always enforced: if replicas=3, the count will always return to 3 regardless of failures. 
- **Key interview answer:** "Deployment manages replicas. Replica is independent — if pods die, no one recreates them. Deployment ensures the desired state is always maintained." 

### Editing Deployments

- **Via CLI:** `kubectl edit deploy <name>` opens the YAML in-editor; change `replicas` value, save with `Escape → :wq → Enter` — changes apply immediately. 
- **Via UI:** GKE Workloads → select deployment → Edit option available. 
- **View YAML:** `kubectl get deploy <name> -o yaml` outputs the full manifest. 
- Both approaches are equivalent; CLI is preferred for production with proper approvals.

## Services and Networking

### Why Not IP-to-IP?

- Kubernetes kills and recreates pods with new IPs; hardcoded IP communication breaks. 
- Elastic IPs are an AWS concept, not applicable at Kubernetes scale (thousands of containers). 
- **Solution:** Communicate using **service names** — the service name is stable even when pod IPs change. 

### Service Types

|       Type        |      Scope      |                               Use Case                                |
|-------------------|-----------------|-----------------------------------------------------------------------|
| **Load Balancer** | Internet-facing | Expose web servers, frontend apps publicly                            |
| **NodePort**      | Node-level      | Communication between tools on the same node (e.g., Jenkins + ArgoCD) |
| **ClusterIP**     | Cluster-wide    | Internal pod-to-pod communication across nodes                        |

- Load Balancer assigns an **external/public IP**; takes ~30 seconds to provision. 
- NodePort: only accessible if you are within the same node. 
- ClusterIP: accessible from anywhere within the same cluster (e.g., all Batch 45 students share one cluster).

## Stateful Sets, PV, and PVC

### Deployment Limitation

- All pods in a Deployment run the **same image** — suitable when all replicas are identical. 
- When different application variants are needed (e.g., Android app, iOS app, TV app, mobile web), Deployment fails — **StatefulSet** is required. 

### Netflix Analogy (PV/PVC)

- **Persistent Volume (PV):** The data/movie itself (e.g., the movie "Ramayan" uploaded by an admin). 
- **Persistent Volume Claim (PVC):** A user (container/pod) claiming and binding to that data. 
    - **Sunil's behavior:** Watches halfway, leaves — container and PVC remain open/claimed. 
    - **Rita's behavior:** Watches the entire movie in one session — container created, PVC claimed, movie completes, everything released. 
    - **Sonindu's behavior:** Opens multiple movies without completing any — multiple containers and PVCs created simultaneously. 
- Netflix logic: up to **5 resume points** can be held; opening a 6th releases the first. 
- When a student completes all course modules (100%), all containers are released and CPU/memory returns to the pool. 

### LMS Demo (Live Illustration)

- Vikas demonstrated the concept using his own LMS (CloudDevOpshop), showing a student (Sanket, Batch 45) with 9% course completion and 12 hours spent. 
- Chapters completed = PVC released; chapters in progress = PVC still claimed and running. 
- Course progress and time-spent are **independent metrics**; rewatching a video increases time but not progress. 

### Key Concepts

- **Bind/Mount:** "Bind" = connected; "Mount" = attached to a location — PV is attached/mounted to the application. 
- **ConfigMap:** Stores **non-sensitive** configuration data (key-value pairs) used to connect pods to PVs or pass environment config; does not require encryption. 
- **Secret:** Stores **sensitive** information (tokens, passwords, API keys); base64-encoded in Kubernetes (easily decoded), hence Vault is preferred in production. 
- **Job:** Performs a specific activity at a particular time; created, executed, and completed — one-time or scheduled tasks. 
- **CronJob:** Scheduled/recurring jobs (student-raised example).

## Jenkins Deployment on Kubernetes (Live Demo)

### Steps Performed

1. **Create pod:** `kubectl run jenkins --image=jenkins/jenkins:lts` 
2. **Verify:** `kubectl get pod` — Jenkins pod running. 
3. **Expose as Load Balancer:** Navigate to Workloads → Jenkins pod → Expose → Port 8080 → Load Balancer. 
4. **Get external IP:** `kubectl get svc` — wait ~30 seconds for IP to provision. 
5. **Retrieve unlock password without entering container:**
    - `kubectl exec <pod-name> -- cat /var/jenkins_home/secrets/initialAdminPassword` 
    - Both `exec -it` (interactive shell) and direct command execution are valid approaches. 
6. **Access Jenkins:** Paste external IP + port 8080 into browser — Jenkins unlock screen appears. 

### Key Notes

- Kubernetes uses `bash` for exec; Docker uses `/bin/bash` — interviewers will understand both. 
- If a pod is deleted, the Deployment automatically recreates it; always delete the **Deployment**, not just the pod, to fully remove an application. 
- `kubectl delete pod <name>` only removes the pod; deployment will recreate it.

## 📝 Technical Corrections (Use These in Interviews)

A few points from class were simplified for teaching. In an interview, use the technically accurate version:

| Topic | Said in class | Accurate version for interviews |
|-------|---------------|---------------------------------|
| ReplicaSet | No auto-recovery if a pod dies | A **ReplicaSet does recreate** pods to keep the count. A **bare Pod** (`kubectl run`) is never recreated. A Deployment manages ReplicaSets and adds **rolling updates, rollback and revision history**. That's why we use Deployments. |
| `kubectl run --replicas=3` | Creates 3 pods | The `--replicas` flag was removed. `kubectl run` now creates a **single bare pod**. Use `kubectl create deployment nginx --image=nginx --replicas=3`. |
| StatefulSet | Needed for different app variants (Android/iOS/TV) | Different variants = **separate Deployments**. A StatefulSet is for **stateful apps** (databases, Kafka, Zookeeper) that need a **stable pod name, stable DNS, ordered start/stop and their own PVC per pod**. |
| Container runtime | GKE uses Docker | GKE uses **containerd** (Docker support/dockershim was removed in Kubernetes 1.24). Docker-built images still run fine. |
| NodePort | Only accessible within the same node | NodePort opens the same port (30000–32767) on **every node**. It's reachable via `<any-node-IP>:<nodePort>`, including from outside if the firewall allows. |
| Service types & kube-proxy | Kube-proxy has 3 service types | Service types are part of the **Service API object**. **Kube-proxy** implements Service routing on each node using iptables/IPVS rules. |
| Kubelet | Reports status to master | Kubelet **starts and monitors the pod's containers** (via the runtime), runs probes **and** reports node/pod status to the API server. |
| Gcloud SDK | `gcloud configure` | Run **`gcloud init`** (or `gcloud auth login` + `gcloud config set project <id>`). Then install the auth plugin: `gcloud components install gke-gcloud-auth-plugin`. |
| E2 Standard 2 | 1 core, 8 GB | **2 vCPUs** (1 physical core shared as 2 threads), **8 GB RAM**. |
| Ingress | Raw Ingress is being deprecated | The **Ingress API is stable but frozen**. **Gateway API** is its successor. The community **ingress-nginx** controller was announced for retirement, so new setups should look at Gateway API implementations or other supported controllers. |
| Jenkins via `kubectl run` | Deployment recreates the pod if it's deleted | `kubectl run` creates a **bare pod**, so it is **NOT recreated** if deleted. Its `/var/jenkins_home` data is also lost without a PVC. For real use: Deployment/StatefulSet + PVC, or the official **Jenkins Helm chart**. |
| Secrets | Base64 only | Base64 is **encoding, not encryption**. In production: enable **encryption at rest** (GKE application-layer secrets encryption with Cloud KMS), use **RBAC**, and bring in external secrets via **Vault / GCP Secret Manager / AWS Secrets Manager** using the Secrets Store CSI Driver or External Secrets Operator. |

# 🎯 20 Interview Questions & Answers

**Q1. Explain the Kubernetes architecture.**
**A:** There are two parts.
- **Control plane:** the **API Server** is the front door for every request, **etcd** stores the cluster state, the **Scheduler** picks a node for new pods and the **Controller Manager** runs reconciliation loops (Deployment, ReplicaSet, Node controllers).
- **Worker nodes:** the **kubelet** runs and monitors pods, **kube-proxy** handles Service networking and the **container runtime** (containerd) runs containers.

In GKE, Google manages the control plane and we manage the workloads and node pools.

**Q2. What happens when you run `kubectl create deployment nginx --image=nginx`?**
**A:**
1. kubectl reads the kubeconfig and sends the request to the API Server.
2. The API Server authenticates and authorizes it, then stores the request in etcd.
3. The Deployment controller creates a ReplicaSet, and the ReplicaSet controller creates the Pod objects.
4. The Scheduler assigns each pod to a node.
5. The kubelet on that node tells containerd to pull the image and start the container, then reports the status back.

**Q3. What is a kubeconfig file?**
**A:** A YAML file, by default at `~/.kube/config`. It holds the **clusters** (API endpoint + CA cert), **users** (credentials/auth plugin) and **contexts** (cluster + user + namespace). On GKE, `gcloud container clusters get-credentials` creates it. Switch contexts with `kubectl config use-context <name>`.

**Q4. Pod vs ReplicaSet vs Deployment?**
**A:**
- **Pod:** the smallest unit, with one or more containers that share network and storage.
- **ReplicaSet:** keeps N identical pods running.
- **Deployment:** manages ReplicaSets and adds rolling updates, rollback and revision history.

In practice, we never create ReplicaSets directly. We always use Deployments.

**Q5. Why should pods communicate using Service names instead of IPs?**
**A:** Pods are ephemeral. Whenever a pod is recreated, rescheduled or scaled, it gets a new IP. A Service gives a **stable virtual IP and DNS name** (`my-svc.my-namespace.svc.cluster.local`), and CoreDNS resolves it. The Service then load-balances to whichever healthy pods match its selector at that moment.

**Q6. ClusterIP vs NodePort vs LoadBalancer?**
**A:**
- **ClusterIP** (default): an internal virtual IP, reachable only inside the cluster. Used for backend APIs and databases.
- **NodePort:** exposes a port (30000–32767) on every node's IP. Used for testing or on-prem setups.
- **LoadBalancer:** asks the cloud provider for an external load balancer with a public IP. Used for internet-facing apps.

In production, we usually put **one Ingress/Gateway** in front instead of creating a LoadBalancer per service, which saves cost and public IPs.

**Q7. What is a Namespace, and how have you used namespaces?**
**A:** A namespace is logical isolation inside a cluster for names, RBAC, ResourceQuotas and NetworkPolicies. Typical layout: `monitoring` (Prometheus/Grafana), `ci-cd` (Jenkins/Argo CD), plus one namespace per team or project. Dev and QA can share a cluster with separate namespaces, but **prod gets its own cluster** for security, blast radius and compliance.

**Q8. Is a namespace a security boundary?**
**A:** Not by itself. By default, pods in different namespaces can still talk to each other. You need **RBAC** for API access, **NetworkPolicies** for traffic, **ResourceQuotas/LimitRanges** for resources and **Pod Security Admission** for pod privileges. For strong isolation, use separate clusters.

**Q9. How do you scale a Deployment?**
**A:** Three options:
- `kubectl scale deploy <name> --replicas=5`
- `kubectl edit deploy <name>`
- Change `replicas:` in the YAML in Git and apply it. This is preferred because Git stays the source of truth.

For automatic scaling, use an **HPA**, which needs resource requests and metrics-server. Note that a manual `kubectl edit` in prod causes drift from Git, and GitOps tools like Argo CD will revert it.

**Q10. What is a StatefulSet, and how is it different from a Deployment?**
**A:** A StatefulSet gives each pod:
- a **stable name** (`mysql-0`, `mysql-1`)
- **stable DNS** through a headless Service
- **ordered** creation, scaling and deletion
- its **own PVC** through `volumeClaimTemplates`, which stays with the pod even after it is rescheduled

Deployment pods are interchangeable and share one template. Use StatefulSets for databases, Kafka, Elasticsearch and Zookeeper.

**Q11. What is a Headless Service?**
**A:** A Service with `clusterIP: None`. It has no virtual IP and no load balancing. A DNS lookup returns the **pod IPs directly**, and each StatefulSet pod gets its own record, e.g. `mysql-0.mysql.default.svc.cluster.local`. This is required for StatefulSets, where clients need to reach a specific replica, such as writing only to the DB primary.

**Q12. Explain PV, PVC and StorageClass.**
**A:**
- **PV:** an actual piece of storage, such as a GCP Persistent Disk or AWS EBS.
- **PVC:** a pod's **request** for storage (size + access mode).
- **StorageClass:** a template that enables **dynamic provisioning**, so when a PVC is created, the cloud disk is created automatically. GKE's default is `standard-rwo`.

The pod mounts the PVC. *Netflix analogy:* the PV is the movie stored on the server, the PVC is your request to watch it, and your session binds to it.

**Q13. What are access modes and reclaim policies?**
**A:**
- **Access modes:** `ReadWriteOnce` (one node can mount it read-write, e.g. a block disk), `ReadOnlyMany`, `ReadWriteMany` (many nodes, needs NFS/Filestore/EFS) and `ReadWriteOncePod`.
- **Reclaim policy:** `Delete` (the disk is deleted along with the PVC, the default for dynamic provisioning) or `Retain` (the disk is kept for manual recovery). Use `Retain` for critical production data.

**Q14. ConfigMap vs Secret?**
**A:**
- **ConfigMap:** non-sensitive config (URLs, feature flags, config files).
- **Secret:** sensitive data (passwords, tokens, TLS certs). It is base64-encoded, which is **not encryption**.

Both can be used as env vars or mounted as files. To secure Secrets in production: encryption at rest with KMS, tight RBAC, and external managers such as Vault or GCP Secret Manager synced in through External Secrets Operator or the CSI driver. Never commit secrets to Git.

**Q15. Job vs CronJob?**
**A:**
- **Job:** runs pods until the task **completes successfully**, e.g. a DB migration or a batch report. It supports `completions`, `parallelism` and `backoffLimit`.
- **CronJob:** creates Jobs on a **schedule** (cron syntax), e.g. a nightly backup at 2 AM: `schedule: "0 2 * * *"`.

**Q16. How do you run a command inside a pod without logging in?**
**A:** Use `kubectl exec <pod> -- <command>`, e.g. `kubectl exec jenkins -- cat /var/jenkins_home/secrets/initialAdminPassword`. For an interactive shell: `kubectl exec -it <pod> -- /bin/bash` (or `sh` if bash isn't in the image). For a multi-container pod, add `-c <container>`.

**Q17. What do `kubectl get`, `describe`, `edit`, `delete`, `logs` and `exec` each do?**
**A:**
- `get`: list resources (`-o wide`, `-o yaml`)
- `describe`: details + **events** (the first step in troubleshooting)
- `edit`: live-edit the YAML
- `delete`: remove a resource
- `logs`: container logs (`--previous` for a crashed container, `-f` to follow)
- `exec`: run a command in a container

**Q18. What is HPA, and how is KEDA different?**
**A:**
- **HPA** scales the replica count based on **CPU/memory or custom metrics**. It needs metrics-server and resource requests.
- **KEDA** scales based on **events**, such as Kafka lag, SQS/Pub/Sub queue length, cron schedules or Prometheus queries, and can **scale to zero**.

Use HPA for web traffic and KEDA for queue workers and event-driven jobs.

**Q19. What is Ingress, and why use it instead of multiple LoadBalancers?**
**A:** Ingress provides **L7 HTTP routing**: host-based (`api.shop.com`) and path-based (`/cart`, `/payment`), plus TLS termination. One Ingress controller behind **one** load balancer can serve many services, which saves cost and public IPs. **Gateway API** is the newer, more expressive successor and is supported on GKE.

**Q20. Why should production be a separate cluster?**
**A:**
- **Blast radius:** a dev mistake or a cluster upgrade can't take down prod.
- **Security and compliance:** separate IAM/RBAC and audit scope.
- **Different policies:** autoscaling, node sizing, maintenance windows and backups.
- **Upgrade testing:** upgrade dev/stage first, then prod.

Common pattern: separate clusters for dev, stage and prod, with namespaces per team or app inside each.

# 🛠️ 20 Scenario-Based Questions & Answers

**S1. You deleted a pod, but it came back. A teammate is confused. Explain.**
**A:** The pod is owned by a Deployment → ReplicaSet. The ReplicaSet controller sees that actual replicas (2) don't match desired replicas (3) and creates a new pod (with a new name and IP). To remove the app permanently, delete the **Deployment** (`kubectl delete deploy <name>`) or scale it to 0. Check the owner with `kubectl get pod <pod> -o jsonpath='{.metadata.ownerReferences[0].kind}'`.

**S2. You deleted the Jenkins pod created with `kubectl run`. It did NOT come back, and all Jenkins jobs were lost. Why, and how would you fix this design?**
**A:** `kubectl run` creates a **bare pod** with no controller, so nothing recreates it. Data in `/var/jenkins_home` was in the container filesystem, so it was lost with the pod.

Fix:
- Deploy Jenkins as a **StatefulSet or Deployment (replicas: 1)** with a **PVC** mounted at `/var/jenkins_home`, or use the official **Jenkins Helm chart**.
- Back up the PVC (volume snapshots).
- Expose it through Ingress with TLS rather than a public LoadBalancer.

**S3. `kubectl get pods` gives "The connection to the server localhost:8080 was refused".**
**A:** kubectl has no valid kubeconfig, so it falls back to localhost. Run `gcloud container clusters get-credentials <cluster> --region <region> --project <project>`. On a local laptop, also install `gke-gcloud-auth-plugin`. Check with `kubectl config current-context` and `kubectl config get-contexts`.

**S4. A LoadBalancer Service shows EXTERNAL-IP `<pending>` for a long time.**
**A:**
1. Run `kubectl describe svc <name>` and read the events.
2. Check the project quota for external IPs and forwarding rules.
3. Check that the Compute Engine API is enabled and that no org policy blocks external LBs.
4. On Minikube/kind there is no cloud LB at all, so use `minikube tunnel` or NodePort.

Normal provisioning on GKE takes about 30–60 seconds.

**S5. Jenkins is exposed through a LoadBalancer, but the browser times out at `http://<EXTERNAL-IP>:8080`.**
**A:**
- Check that the Service `port`/`targetPort` matches 8080.
- Check that the selector matches the pod labels with `kubectl get endpoints <svc>`. If it's empty, there's a label mismatch.
- Check that the pod is Running and Ready.
- Check that you're using http, not https.
- Check any firewall rules.

Test from inside the cluster with `kubectl run tmp --rm -it --image=busybox -- wget -qO- http://<svc>:8080`.

**S6. The app worked yesterday, but after a pod restart the backend can't connect to the DB. The config has a hardcoded IP.**
**A:** The DB pod was recreated with a new IP. Replace the IP with the **Service DNS name** (e.g. `mysql.db.svc.cluster.local:3306`), store it in a **ConfigMap**, and restart the app (`kubectl rollout restart deploy <app>`). For a StatefulSet DB, use a headless Service with the stable pod DNS name (e.g. `mysql-0.mysql`).

**S7. A teammate changed replicas from 3 to 1 using `kubectl edit` in prod. The next day it went back to 3. Why?**
**A:** Most likely GitOps (Argo CD/Flux) or a CI pipeline re-applied the manifest from Git, which is the source of truth. An HPA can also override manual replica changes. Lesson: change the replica count through a **Git PR**, not `kubectl edit`, in production.

**S8. You need to run MySQL on Kubernetes with data that survives pod restarts.**
**A:** Use a **StatefulSet** with `volumeClaimTemplates` (each replica gets its own PVC on a Persistent Disk), a **headless Service** for stable DNS, a **Secret** for the root password, a `Retain` reclaim policy, and regular backups/snapshots. Better still for production: a managed DB (**Cloud SQL / RDS**) or a proper operator.

**S9. A PVC is stuck in `Pending`.**
**A:** Run `kubectl describe pvc <name>`. Common causes:
- The StorageClass doesn't exist or there is no default.
- The requested access mode isn't supported (e.g. `ReadWriteMany` on a block disk → use Filestore/NFS).
- No matching PV for static provisioning.
- `WaitForFirstConsumer` mode, where the PVC binds only after a pod uses it. That's normal.
- Disk quota exceeded.

**S10. A pod using a PVC is stuck in `ContainerCreating` after being rescheduled to another node.**
**A:** A `ReadWriteOnce` disk can attach to only **one node**. It may still be attached to the old node, or the new node may be in a different **zone** than the disk. Check `kubectl describe pod` for "Multi-Attach error" or volume node affinity conflicts. Fix: wait for detach or remove the stuck VolumeAttachment, use zone-aware scheduling, or use regional PDs for HA.

**S11. The security team found DB passwords in a ConfigMap in Git. What do you do?**
**A:**
1. **Rotate the password immediately**, since it is compromised.
2. Move it to a Secret, and keep its value out of Git. Pull it from **Vault/GCP Secret Manager** using External Secrets Operator, or use Sealed Secrets/SOPS for encrypted secrets in Git.
3. Clean the Git history.
4. Enable KMS encryption at rest.
5. Restrict Secret access with RBAC.
6. Add secret scanning (gitleaks/trufflehog) to CI.

**S12. Someone with read access ran `kubectl get secret db-pass -o yaml` and decoded the password. How do you prevent this?**
**A:** Base64 is not protection. Restrict `get/list` on `secrets` with **RBAC**, so developers get Roles without secret access. Audit access with Cloud Audit Logs. Use external secret managers with short-lived credentials, and prefer **Workload Identity** so apps reach cloud services with no static keys at all.

**S13. Your QA and Dev teams share one cluster. QA load tests are starving Dev pods.**
**A:**
- Put them in separate namespaces with a **ResourceQuota** (CPU/memory/pod limits per namespace) and a **LimitRange** (default requests/limits).
- Optionally use separate **node pools** with taints/tolerations, and PriorityClasses.
- For heavy load testing, use a temporary separate cluster.

**S14. You need a nightly 2 AM database backup on Kubernetes.**
**A:** Create a **CronJob** with `schedule: "0 2 * * *"`, the backup image, credentials from a Secret, and output to GCS/S3. Set `concurrencyPolicy: Forbid` so runs don't overlap, plus `successfulJobsHistoryLimit`/`failedJobsHistoryLimit`, and `backoffLimit`. Note that CronJob times use the controller's timezone (UTC by default), so set `timeZone: "Asia/Kolkata"`. Alert on failed Jobs.

**S15. A one-time DB migration Job keeps failing and creating many pods.**
**A:** Run `kubectl describe job` and `kubectl logs job/<name>`. Set `backoffLimit` (e.g. 3) to cap retries, and set `activeDeadlineSeconds` and `ttlSecondsAfterFinished` for cleanup. Fix the root cause, usually a wrong DB endpoint or credentials, or the DB not being ready yet. Run migrations as a pre-deploy step in the pipeline or as a Helm hook.

**S16. Traffic spikes every evening at 8 PM and pods get overloaded before HPA reacts.**
**A:**
- Tune the **HPA** (lower CPU target, faster `scaleUp` behavior) and keep enough `minReplicas`.
- Since the spike is predictable, use a **KEDA cron scaler** or a CronJob to scale up at 7:45 PM.
- Enable the **Cluster Autoscaler** with node headroom.
- Make sure readiness probes and image pull times are fast.

**S17. Your app processes messages from Pub/Sub/Kafka. The queue builds up, but CPU stays low, so HPA doesn't scale.**
**A:** CPU isn't the right signal. Use **KEDA** with a Pub/Sub or Kafka scaler based on **queue depth/consumer lag**. It scales out as the backlog grows and can scale to zero when the queue is empty, which saves cost.

**S18. You want `/cart` and `/payment` on one domain with HTTPS, without 2 LoadBalancers.**
**A:** Create both services as **ClusterIP**. Add an **Ingress** (or Gateway API HTTPRoute) with path rules `/cart → cart-svc` and `/payment → payment-svc`. Terminate TLS with a cert from cert-manager (Let's Encrypt) or a Google-managed certificate. Point DNS to the single Ingress IP.

**S19. Your GCP bill jumped after a week of practice.**
**A:** The GKE nodes, disks (PVs with the `Retain` policy) and LoadBalancers/external IPs were left running.

Fix:
- Delete the cluster after each session.
- Check for **orphaned disks** (Compute Engine → Disks) and **static IPs/forwarding rules**.
- Use **Spot VMs** for practice node pools, or Autopilot.
- Set **budget alerts** in Billing.

Deleting the cluster doesn't always delete retained PVs or reserved IPs, so verify manually.

**S20. A student created a cluster with 3 nodes "per zone" in a regional cluster and got 9 nodes. How do you explain and fix it?**
**A:** In a **regional** GKE cluster, the node count is **per zone**, and the default region has 3 zones, so 3 × 3 = 9 nodes. Fix: set the node count to 1 per zone (3 total), or create a **zonal** cluster for learning. In production, regional clusters are preferred for HA, because the control plane and nodes are spread across zones.
